## Membership migration update (2026-08-09)

Implemented locally and tested:
- Shared multi-institute contracts and strict status model (`pending`, `active`,
  `rejected`, `suspended`, `revoked`).
- Session-only active membership selection and explicit legacy compatibility
  bridge; only active memberships of the authenticated user can be selected.
- Institute Admin includes the Teacher capability set within the same active
  institute without a duplicate membership or client-side escalation.
- Authentication policy accepts an approved active membership and retains the
  legacy `users/{uid}` assignment only while no membership record exists.
- Shared analyzer: no issues. Shared tests: 69 passed.

Blocked safely, not bypassed:
- The deployed-style Cloudflare Worker currently uses an end-user Firebase ID
  token. It cannot write or approve callable-only Firestore membership records
  without a separately approved least-privilege server-to-server Firebase
  credential. Allowing client Firestore writes merely to make the Worker work
  would weaken the membership boundary and was not done.
- Therefore join, approval, active-institute switching UI, migration/backfill,
  and Worker membership endpoints are not represented as deployed features.

No deployment, publishing, data migration, real FCM delivery, or real SMS
delivery occurred in this update.
